# 1.1.0 Safe Updater & Private Source Foundation Roadmap

Stand: 2026-06-19

Status: **Safe Updater offline feature complete; live actions remain operator-gated**

## Goal

After `1.0.0`, Odysseus gets a complete Safe Updater Module as the first finished 1.1 feature, and uses that updater foundation to prepare Nextcloud as a safe private source provider and Universal Inbox MVP with no-delete/copy-only/review-gated policy. Telegram Voice remains an optional follow-up after the updater and Nextcloud foundation are stable.

Primary feature:
- `Odysseus Updater Module`

Secondary track:
- Nextcloud Source Provider and Universal Inbox MVP foundation.

## Product Decision

`1.1.0` is not only a Nextcloud source-provider preparation track. Its first completed user-visible feature must be an **Odysseus Updater Module**.

The updater is the safety and operations basis for later Nextcloud, Telegram, host, and live deployment work. It plans, checks, prepares, executes only when explicitly allowed, and records update attempts. It must support dry-run planning, backup gates, test gates, rollback/hold guidance, and audit/handoff output. It must never become a blind automatic deploy path.

Nextcloud remains important, but it is now the secondary 1.1 track after the updater feature is defined and at least partially completed. Nextcloud is a Source Provider and Universal Inbox, not automatic Memory truth. Original files stay protected. Odysseus may later produce derived data such as ledger entries, tags, sidecars, RaptorGraph provenance, and Review Queue artifacts, but no live Nextcloud action is implied by this roadmap.

Sequencing note:

- `V11-1` through `V11-4` may be closed as already-opened offline foundation work because they do not start live Nextcloud, host, provider, Telegram, backup, restore, or network actions.
- New Nextcloud implementation slices after `V11-4` stay queued until `UPD9` is done or consciously accepted as Partial by Charlie.
- The updater track is complete through `UPD9` as an offline, non-live feature as of commit `58bdf6af`; further Nextcloud work may proceed only in the same gated, offline style unless a separate live Go is granted.

Hard MVP boundaries:
- No human Nextcloud admin user for automation.
- Dedicated user recommended as `odysseus-intake`, initially without delete rights.
- No-delete, no-move, no-overwrite, copy-only, and review-gated behavior are hard MVP limits.
- Real updater execution, host action, Nextcloud action, Telegram action, provider action, export/import, rebuild, backup, restore, or deploy remains operator-gated.

Updater operator contract for `UPD0`:

- The `Odysseus Updater Module` is the first planned completed `1.1` feature. `UPD9` is the handoff point that may declare it the first completed `1.1` feature, or consciously mark it `Partial` if evidence is still missing.
- Real update execution remains operator-gated at every stage. Contract completion, green tests, and ready plans do not authorize a live deploy by themselves.

Required updater modes and meanings:

- `dry_run`: build a deterministic update plan, required gates, and redacted operator guidance only. No live mutation, deploy, backup, restore, host, git, or network execution is implied.
- `preflight`: evaluate supplied state snapshots and classify whether the requested update can advance to later gates. This is read-only validation, not command execution.
- `backup_required`: declare that `pre-update` snapshot evidence, `restic check`, and restore smoke evidence must be present and green before any operator could consider a live update path.
- `tests_required`: declare that the required focused test evidence must be green before an operator can move past hold state.
- `hold`: the default non-live decision state whenever required evidence is incomplete, ambiguous, stale, or awaiting operator review. `hold` is safe pause language, not failure by itself.
- `ready_for_operator_go`: all offline planning and required gate evidence known to this contract are satisfied, and the updater may be handed to an operator for an explicit Go or No-Go decision. This is still not deployment.
- `deployed_by_operator`: reserved audit label for a later operator-confirmed live execution event. This roadmap does not perform or promise that event.
- `smoke_required`: after any future operator-executed deployment, smoke verification evidence must be recorded before the outcome can be treated as stable.
- `rollback_or_hold`: decision language for operator handoff when post-deploy evidence or smoke results are not acceptable. It never means automatic destructive rollback; it means the operator must choose rollback, hold, or another explicit safe response outside this docs-only slice.

Required gate flow language:

- Dry-run comes first and produces only plan data, gate requirements, and audit-safe handoff text.
- Preflight decides whether scope, worktree, refs, and named prerequisites are sufficiently clean to continue planning.
- Backup gate decides whether required backup and restore evidence is good enough for the requested risk level.
- Test gate decides whether required focused tests are green and whether any remaining failures force `hold`, `partial`, or `no_go`.
- Deploy hold is the standing boundary between offline readiness and any future live action. The updater must stop at `hold` or `ready_for_operator_go` until a human operator explicitly chooses otherwise.
- Smoke is a required evidence stage only after a future operator-led deployment. Smoke failure feeds decision language, not destructive automation.
- Rollback/Hold is recorded as operator decision wording and rationale. The updater may recommend `rollback_or_hold`, but it must not auto-run destructive rollback commands.
- Audit/Handoff output must stay safe to persist: plan id, refs, gate states, decision labels, timestamps, reasons, and redacted notes only, with no credentials, tokens, passwords, chat IDs, host output, or private provider/source output.

Updater decision language:

- `Go`: the updater contract, offline models, required focused tests, and audit-safe handoff are complete enough for the updater to be treated as the first completed `1.1` feature, while real execution remains separately operator-gated.
- `Partial`: the updater contract and some offline implementation are usable, but one or more named blockers remain, such as missing backup evidence, incomplete test coverage, missing entrypoint choice, or unresolved operator-review points.
- `No-Go`: stop the updater path because safety gates are broken, scope is violated, secrets or private output would leak, or the updater would imply live execution without explicit operator control.
- `Deferred`: intentionally postpone live-execution-adjacent work, operator deployment, destructive rollback automation, or other later-scope behavior while preserving the offline updater contract and handoff evidence.

- `read`
- copy planning
- sidecar or review-artifact planning
- tag projection planning
- redacted metadata planning for ledger, routing, and provenance

Forbidden operations in `1.1` policy scope:

- `delete`
- `move`
- `overwrite`
- admin-user usage for normal intake work
- automatic canonical promotion from `Inbox` to any final destination
- persistence of private content or provider/source output in logs, prompts, tests, or handoffs

Review-language defaults for operator handoff:

- `Go`: policy is documented, scope is clean, the next slice may continue in its allowed path, and no live mutation is implied.

- uncertain target folder

- partial extraction
- conflict with existing destination candidate
- policy uncertainty

Safe defaults regardless of route:

- no delete, no move, no overwrite
- designated user only

- narrow root path or endpoint scope

- no private content in logs, handoffs, or tests

## Go / Partial / No-Go / Deferred

`Go` for starting 1.1 implementation:
- `1.0.0` Go or explicitly accepted Partial handoff is documented.
- Worktree has no foreign staged files or hotfile conflicts.
- Alice/Bob allowed paths are exact.
- No live action is required for the first implementation slices.

`Go` for the 1.1 updater feature:
- Offline Update Plan, Preflight, Backup Gate Evidence Model, Test Gate, Command Plan, Audit Ledger, and Operator Runbook are complete and focused tests are green.
- Updater blocks deployments without backup/restore evidence.
- Updater emits audit-safe handoffs and rollback/hold decisions without secrets.
- Any real update execution remains operator-gated and is not implied by green unit tests.

`Partial` for 1.1:
- Updater roadmap/models/tests are ready, but live update execution, real backup/restore evidence, or a local CLI/API entrypoint remains pending.
- Nextcloud roadmap and offline models/tests may exist, but live Nextcloud credentials, actual folders, backup/restore, or manual inbox proof remain pending.
- Backup artifacts may exist, but real `pre-update` snapshot plus restore smoke is not yet green.

`No-Go`:
- `1.0.0` handoff is absent or contradictory.
- Secrets or private provider/source output would leak.
- Updater allows deletes, force/rewrite operations, unbounded live command execution, or deployment without gates.
- Source-provider work would require live credentials, network, host mutation, or real Nextcloud writes before gates are ready.
- No-delete/copy-only/review-gated policy is not enforceable or not documented.

`Deferred`:
- Telegram Voice download/STT/reply.
- Server-side Nextcloud app.
- Live Nextcloud writes.
- Host backup/restore execution.
- Fully automatic update execution.
- Destructive rollback automation.
- Research/accelerator tracks.
